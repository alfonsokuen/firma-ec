# F3.5 WhatsApp Inbox Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recomendado) o `superpowers:executing-plans` para implementar este plan task-by-task. Cada step usa checkbox (`- [ ]`) para tracking. Tasks marcadas `[parallel]` se pueden dispatch en paralelo; el resto es secuencial. **Activar `qa-verify` siempre** (respaldo + cambio + verificación + push confirmado + memoria).

**Goal:** PWA route `/inbox` + backend Fastify mínimo + Evolution instance `firmar-ec` para flujo WA-mediated de firma/verificación de PDFs con privacidad-first (cifrado client-side, OTP, hard-delete 24h). Entregable: tag `v0.5.0-rc1` con E2E Playwright PASS y cross-test manual con `.p12` ArgosData real.

**Architecture:** Fastify + Prisma 5 backend (~300 LOC) sobre Patroni 16 HAProxy + Redis HA DB 10 + R2 bucket `firmar-ec-inbox` con lifecycle 24h. Evolution API instance dedicada `firmar-ec` en stack existente (replicar patrón `puntual-idkmanager`). Nuevo paquete `packages/inbox-crypto` (AES-256-GCM + PBKDF2-SHA256 600k iter via Web Crypto). Nueva ruta lazy `/inbox` en PWA que reusa flujos `/firmar` y `/verificar` existentes. Outbox opt-in click-to-send via Evolution. Privacy invariants: backend nunca ve plaintext, OTP solo en Argon2id, phones HMAC-hashed, audit log encriptado con clave separada.

**Tech Stack:** Node.js 22 LTS + Fastify 5 + Prisma 5 + zod 3 + jose 5 (JWT) + argon2 0.41 + ioredis 5 + @aws-sdk/client-s3 3.700+ (con `AWS_REQUEST_CHECKSUM_CALCULATION=WHEN_REQUIRED`) + axios (Evolution client) + vitest 2 + Playwright 1.49 + Svelte 5 + Pino logger + Docker multi-stage + Caddyfile + Traefik file middleware reuse.

**Spec reference:** `docs/superpowers/specs/2026-05-09-firma-ec-F3.5-whatsapp-inbox-design.md` (decisiones 1-13, arquitectura §2, UX §3, privacy §4, quotas §5, tests §6, out-of-scope §7, aceptación §8).

### `packages/inbox-crypto`

- [ ] **T6 [parallel]** — Bootstrap `packages/inbox-crypto`
  - **Create:** `packages/inbox-crypto/package.json` (workspace `@firma-ec/inbox-crypto`, type module, exports `./src/index.ts`).
  - **deps:** ninguna runtime (solo Web Crypto / Node `crypto.subtle`); **devDeps** `vitest`, `typescript`.
  - **Create:** `src/kdf.ts`:
    ```ts
    export async function deriveKey(otp: string, salt: Uint8Array): Promise<CryptoKey> {
      const enc = new TextEncoder().encode(otp);
      const baseKey = await crypto.subtle.importKey('raw', enc, 'PBKDF2', false, ['deriveKey']);
      return crypto.subtle.deriveKey(
        { name: 'PBKDF2', salt, iterations: 600_000, hash: 'SHA-256' },
        baseKey,
        { name: 'AES-GCM', length: 256 },
        false,
        ['encrypt', 'decrypt']
      );
    }
    ```
  - **Create:** `src/aead.ts` con `encrypt(key, plaintext) → { iv, ciphertext }` y `decrypt(key, iv, ciphertext) → plaintext`. IV 12 bytes random.

### Webhook + OTP + Rate limit

- [ ] **T11 — `services/otp.ts`**
  - `generateOtp(): string` → 6 dígitos crypto-random.
  - `hashOtp(otp: string): Promise<string>` → Argon2id (m=64MiB, t=3, p=2) + pepper from `INBOX_DEPLOY_SECRET`.

  - Almacenar OTP→pdfId map en Redis `otp:<hash>` SETEX 600s.
  - **Tests:** Argon2 params, hash determinismo (mismo OTP+salt+pepper → mismo hash), brute-force resistance (timing).

- [ ] **T12 — `services/rate-limit.ts`**
  - Token bucket atómico via Lua script en Redis (memoria del patrón en `idkmanager-infra`).
  - Límites: `1 msg / 30s / phone`, `5 PDFs / día / phone`, `10 OTP attempts / hora / phone`.
  - Helper `checkAndConsume(key: string, capacity: number, refillRate: number): Promise<{ ok: boolean, retryAfterS: number }>`.
  - **Tests:** edge cases (refill clock skew, 429 con retry_after correcto, atomicity bajo concurrent).

- [ ] **T13 — `routes/webhook-wa.ts`**
  - POST `/webhook/wa` con `rawBody: true`.
  - Steps:
    1. Verify HMAC header `X-Evolution-Signature` con `WEBHOOK_HMAC_SECRET`. Reject 401 si fail.
    2. Parse Evolution event JSON. Filtrar solo `messages.upsert` con `messageType=documentMessage` y mimetype `application/pdf`.
    3. Idempotency check: `messageId` en `PendingPdf` → 200 sin acción.
    4. Rate limit check (`rl:msg:<phone_hash>` + `rl:pdf:<phone_hash>:<YYYYMMDD>`).
    5. Si pdf > 20MB → reject + reply WA "PDF excede 20MB. Comprímelo o envía por email (próximamente)".
    6. Generate OTP + salt 16 bytes random.
    7. Fetch PDF blob desde Evolution API (`/chat/getBase64FromMediaMessage/<instance>` o equivalente).
    8. Encrypt: `encryptForR2(otp, salt, plaintext)` → `{ iv, ciphertext }`.
    9. PUT R2 con key `<uuid>.bin` body = `iv || ciphertext`.
    10. INSERT `PendingPdf` (otp_hash, sender_phone_hash, message_id, r2_key, salt, size_bytes, ttl_at = now+24h).
    11. Set Redis `otp:<hash>` → `pdfId` SETEX 600.
    12. Reply WA via Evolution.send con texto: "📄 Recibí tu PDF (...) Tu link: app.firmar.ec/inbox?t=<OTP>".
    13. INSERT AuditLog `wa.received` (encrypted payload).
  - **Verify:** test cubre HMAC fail, replay, rate limit, happy path, no-PDF message.

- [ ] **T14 — `routes/inbox-verify.ts`**

  - **Test:** OTP válido → 200 + jwt; inválido → 401.
