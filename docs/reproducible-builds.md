# Reproducible Builds — firma.ec

**Status (2026-05-10):** Quick wins applied in `.github/workflows/release.yml`. Full bit-identical reproducibility is **work in progress**; the README transparency-report claim was reframed from "Reproducible Builds verified" to "roadmap" on 2026-05-10 (commit `ffc7d78`) to match reality.

This document tells the truth about what is and isn't reproducible today, plus the concrete next steps to close the gap.

## What is reproducible today

| Step | Mechanism | Determinism level |
|---|---|---|
| Dependency resolution | `pnpm install --frozen-lockfile` + checked-in `pnpm-lock.yaml` | ✅ Strong — same lockfile → identical `node_modules` tree |
| Source state | Git tag SHA pinned + `actions/checkout@v4 persist-credentials=false` | ✅ Strong |
| Tarball file ordering | `tar --sort=name` (2026-05-10) | ✅ Strong |
| Tarball ownership | `--owner=0 --group=0 --numeric-owner` | ✅ Strong |
| Tarball mtime | `--mtime=@${SOURCE_DATE_EPOCH}` from commit timestamp (2026-05-10) | ✅ Strong |
| Gzip metadata | `gzip -n` strips embedded timestamp+filename (2026-05-10) | ✅ Strong |
| SBOM generation | `anchore/sbom-action` — output may include scan timestamp | ⚠️ Partial — see open issues |
| Build outputs (Astro / Vite) | `pnpm build` — most outputs are content-addressed, hashed | ⚠️ Mostly — see below |

## What is NOT yet reproducible

### 1. Astro/Vite build timestamps in HTML

Astro's default output may include `<!-- generated by Astro vX.Y.Z -->` comments and certain plugins emit build-time strings. Vite's HMR-friendly module IDs are stable, but the `_astro/*` chunk names depend on hash inputs that may shift if dependency order shifts (rare with frozen-lockfile, but possible).

**Status:** Empirically deterministic in our two-run smoke tests, but not contractually guaranteed by Astro/Vite. Needs an explicit `diffoscope` run on the release tarball to confirm.

### 2. PDF.js worker bundling

`pdf.js` v4 is bundled into the PWA worker chunk. Its build output is usually deterministic but the upstream project hasn't committed to Reproducible Builds. Worth pinning to a specific tarball SHA-256 in `pnpm-lock.yaml`.

### 3. SBOM scan timestamps

`anchore/sbom-action` may embed a "metadata.timestamp" field. We override this with `SOURCE_DATE_EPOCH` (2026-05-10) but should verify the resulting SBOM is identical across two runs.

### 4. UnoCSS class ordering

UnoCSS deterministically orders classes by default, but `@unocss/preset-wind4` and runtime scanners can theoretically reorder if file enumeration order differs. We trust the lockfile here but it's not been independently verified.

## How to verify locally

```bash
# 1. Clean checkout at the tag
git clone https://github.com/idkmanager/firmar-ec.git && cd firma-ec
git checkout v0.7.0-rc1

# 2. Build with the SAME env CI uses
export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
pnpm install --frozen-lockfile
pnpm build

# 3. Re-tar with the same flags
tar --sort=name --owner=0 --group=0 --numeric-owner --mtime=@$SOURCE_DATE_EPOCH \
    -cf landing.tar -C apps/landing/dist . && gzip -n -9 landing.tar
tar --sort=name --owner=0 --group=0 --numeric-owner --mtime=@$SOURCE_DATE_EPOCH \
    -cf pwa.tar -C apps/pwa/dist . && gzip -n -9 pwa.tar

# 4. Compare SHA-256 against the release checksums.txt
sha256sum landing.tar.gz pwa.tar.gz

# 5. If hashes diverge, use diffoscope to find the source of non-determinism
diffoscope --html diff-report.html landing.tar.gz <(curl -sL https://github.com/idkmanager/firmar-ec/releases/download/v0.7.0-rc1/landing.tar.gz)
```

## Roadmap to "verified reproducible"

1. **Add `repro-check` CI job** that builds twice (back-to-back) in the same workflow run and asserts `sha256sum` matches between the two. Fails the release if non-deterministic. ⏳
2. **Cross-environment check**: same tag built from Ubuntu 24.04 GitHub runner vs Debian Bookworm container. Detects environment-specific non-determinism. ⏳
3. **`diffoscope` artifact** uploaded to the release on every release. Even when SHAs match, the report proves it. ⏳
4. **Document `SOURCE_DATE_EPOCH` propagation**: confirm every build tool (Astro, Vite, UnoCSS, esbuild, terser) honours it. Open upstream issues where they don't. ⏳
5. **Independent re-build**: external party (or my home PC) runs the local verification above for each tagged release. Publish their attestation alongside. ⏳

## Why this matters

A signature scheme is only as trustworthy as the binary it signs. SLSA L3 + Cosign + Rekor prove **who built the artifact and from what source**, but not **that the artifact corresponds to that source**. Reproducible builds close that gap: any third party can rebuild and verify byte-identical output. Without it, a malicious build server could substitute a trojan and the provenance chain wouldn't catch it.

For a signature product, this matters more than for most. We're committing to it as a roadmap, not a current claim.
