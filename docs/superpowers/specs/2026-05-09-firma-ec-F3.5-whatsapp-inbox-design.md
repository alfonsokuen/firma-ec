# F3.5 — WhatsApp Inbox / Outbox bidireccional para firmar.ec

## 0. Goal

Permitir a usuarios ecuatorianos **firmar o verificar PDFs recibidos por WhatsApp** con cero fricción: el usuario reenvía el PDF al bot oficial de firmar.ec, recibe en respuesta un link único con OTP, abre el link en su celular o PC, ve sus PDFs pendientes en `/inbox`, los firma o verifica con el flujo F3/F2 ya existente y opcionalmente reenvía el resultado al chat original — sin crear cuenta, sin instalar nada extra, manteniendo la promesa **privacy-first** (PDFs cifrados client-side antes de salir del navegador, metadata mínima en backend, hard-delete a las 24h, ningún plaintext atraviesa la base de datos).

> **Por qué F3.5 y no F4 / F5 / F6:** WhatsApp es el canal #1 en Ecuador para circular PDFs administrativos (facturas, contratos, declaraciones, oficios). F3 + F4 ya resolvieron el "cómo firmar"; F3.5 resuelve el **"cómo recibir el PDF a firmar sin convertir el celular en un campo de minas de descargas"**. Es un sprint puente: solo añade superficie de I/O, no cambia el motor cripto.

## 1. Decisiones aprobadas (decision log)

| # | Decisión | Rationale |
|---|---|---|
| 1 | **Auth = OTP por WhatsApp, sin cuentas formales** | Cero formularios, cero contraseñas, cero recuperación de cuenta. El número de WA ya es un identificador legítimo del usuario; el OTP de 6 dígitos vincula sesión ↔ phone hash. Si el user pierde el OTP, el PDF se autodestruye en 24h por TTL — privacy by design. |
| 2 | **Privacy: PDF cifrado client-side antes de subir a R2 (AES-256-GCM)** | Backend solo guarda ciphertext + metadata. La key se deriva del OTP (PBKDF2-SHA256, 600k iter) más un salt almacenado junto al ciphertext. Sin OTP, el blob de R2 es ruido. Mantiene la claim "100% client-side" de F3/F4 — el servidor *jamás* ve plaintext. |
| 3 | **Storage: Cloudflare R2 con lifecycle 24h** | Mismo proveedor que el resto del workspace (idkmanager). Más barato que S3, `WHEN_REQUIRED` checksums (memoria ya documenta el trap). Lifecycle 24h hard delete = límite legal LOPDP claro. |
| 4 | **DB: Patroni 16 (HAProxy `postgres16_postgres:5432`) — nueva DB `firmar_ec_inbox`** | HA, mismo cluster que el resto. NUNCA hardcodear `patroni2`. Sólo metadata: `(otp_hash, sender_phone_hash, message_id, r2_key, salt, ttl_at, status)`. |
| 5 | **Queue / OTP store: Redis HA (`redis-ha:6379`) DB 10** | Rate limit + OTP TTL + outbox jobs. DB 10 reservada (DBs 0-9 ocupadas por servicios existentes). |
| 6 | **Evolution API instance dedicada `firmar-ec`** | Replicar el patrón ya en producción (`puntual-idkmanager`, `cum`, `claude-code`). No tocar instancias activas. Webhook HMAC-validated. |
| 7 | **Backend mínimo: Node.js Fastify + Prisma 5** | Stack ya conocido en el workspace. ~150-300 LOC efectivo. Fastify por throughput (webhook puede ráfagas de 100+ msg/s en horas pico). Prisma por type-safety y migrations versionadas. |
| 8 | **Frontend: nueva ruta `/inbox` en PWA existente** | Reuso del header, theme, CSP, Trusted Types, worker pattern. NO crear app separada. Ruta perezosa (lazy import) para no inflar bundle de los users que solo usan `/firmar` y `/verificar`. |
| 9 | **Outbox: opt-in explícito por click** | Tras firmar/verificar, el user ve "Reenviar al remitente original" — no se manda automáticamente. Esto evita que un atacante que hackee el OTP haga eco de PDFs sin consentimiento del firmante. |
| 10 | **Quotas: 5 PDFs/día/phone, rate limit 1 msg/30s** | Anti-abuse sin formularios. Si un user legítimo necesita más, mandamos a F3.6 (cuentas opcionales). |
| 11 | **Threat model explícito § 6 + audit log cifrado** | Documentamos qué pasa si se compromete backend, R2, Evolution o el celular del user. Audit log en append-only encriptado con clave de despliegue (rotada mensualmente). |
| 12 | **Out-of-scope F3.5 → F3.6+** | Email inbox (SMTP/IMAP), Telegram, SMS, login persistente, multi-firma cross-platform, integración con drives. F3.5 = solo WA. |
| 13 | **Tag deliverable: `v0.5.0-rc1`** | Bump menor sobre v0.4.x (F4). `-rc1` hasta validar con tráfico real (>100 mensajes en una semana). |

### 2.3 Esquema Prisma (DB `firmar_ec_inbox`)

```prisma
model PendingPdf {
  id                String   @id @default(uuid())
  otp_hash          String   @unique   // Argon2id de OTP+pepper
  sender_phone_hash String              // HMAC-SHA256(e164_phone, deploy_secret)
  message_id        String              // Evolution message id (idempotencia)
  r2_key            String              // firmar-ec-inbox/<uuid>.bin
  salt              Bytes               // 16 bytes para PBKDF2 (no secreto)
  size_bytes        Int                 // tamaño plaintext aproximado (telemetría)
  created_at        DateTime @default(now())
  ttl_at            DateTime            // created_at + 24h
  status            String   @default("pending")  // pending | signed | verified | sent | expired | deleted
  consumed_at       DateTime?
  @@index([sender_phone_hash, created_at])
  @@index([ttl_at])
  @@index([message_id])
}

model AuditLog {
  id          String   @id @default(uuid())
  ts          DateTime @default(now())
  event       String   // wa.received | otp.issued | inbox.opened | sign.done | outbox.sent | ttl.cleaned
  payload_enc Bytes    // AES-GCM(JSON, deploy_audit_key) — solo descifrable con key separada
  @@index([ts])
}
```

### 2.4 Endpoints (contratos resumidos)

| Método | Ruta | Auth | Body | Respuesta |
|---|---|---|---|---|
| POST | `/webhook/wa` | HMAC header `X-Evolution-Signature` | Evolution event JSON | `{ ok: true }` 200 |
| GET | `/api/inbox?otp=ABC123` | OTP en query (validar Argon2id) | — | `[{ id, size_bytes, created_at, sender_phone_masked }]` |
| GET | `/api/inbox/:id/blob` | JWT (15min, emitido tras OTP) | — | `application/octet-stream` (ciphertext) |
| GET | `/api/inbox/:id/meta` | JWT | — | `{ salt, iv, sender_phone_masked }` |
| POST | `/api/outbox/send` | JWT | `{ id, signed_pdf_b64, target: "original" \| { phone } }` | `{ ok: true, evolution_message_id }` |
| GET | `/healthz` | none | — | `{ db: ok, redis: ok, r2: ok, evolution: ok }` |

**JWT**: HS256, secret en Docker secret `inbox_jwt_secret`, `sub = otp_hash`, `exp = 15min`. Single-use (revocado en Redis al usar).

## 3. UX flow detallado

### 3.1 Inbound (usuario → bot)

1. Usuario tiene un PDF en WhatsApp (recibido de cliente, SRI, contraparte legal, etc.).
2. Lo reenvía al contacto **firmar.ec — Bot Oficial** (`+593 XX XXX XXXX` — número definido en T6).
3. Bot responde en **<3s**:
   > 📄 Recibí tu PDF (`facturas-julio.pdf`, 384 KB).
   > Tu link para firmarlo o verificarlo:
   > 🔗 https://app.firmar.ec/inbox?t=ABC123
   > ⚠️ El link y el archivo se borran en **24 horas**. Solo tú con este código puedes abrirlo.
4. Si el user manda un mensaje que no es PDF: bot responde con instrucciones cortas + link a https://firmar.ec/como-funciona-wa.

### 3.2 Sesión PWA (`/inbox?t=ABC123`)

1. PWA detecta `?t=` → abre modal "Verifica que eres tú: ingresa los 6 dígitos del link" (anti-shoulder-surfing en links compartidos accidentalmente).
2. User ingresa OTP → POST `/api/inbox/verify` → si OK, recibe JWT + lista de PDFs pendientes.
3. UI muestra cards:
   - Nombre del archivo (extraído de Evolution caption o "documento.pdf").
   - Tamaño, hora recibido, sender phone masked (`+593 9X XXX 4321`).
   - Botones: **Firmar**, **Verificar**, **Descargar (sin firmar)**.
4. Click **Firmar** → fetch ciphertext + meta → decrypt en cliente (Web Crypto, key = KDF(OTP, salt)) → pasa el `Uint8Array` al flujo `/firmar` existente (props `prefilledPdf`).
5. Click **Verificar** → mismo patrón, pasa al flujo `/verificar`.
6. Tras firmar: `DownloadResult.svelte` extiende con tres CTAs:
   - **Descargar** (existente).
   - **Reenviar al remitente original** (NEW) — POST `/api/outbox/send` con `target: "original"`.
   - **Reenviar a otro número** (NEW) — input phone + POST con `target: { phone }`.
7. Toast de confirmación: "Enviado. Mensaje WA: <id>".

### 3.3 TTL / housekeeping

- Cron interno (Fastify `setInterval` 5min): query `PendingPdf where ttl_at < now()` → DELETE R2 object + DELETE row + INSERT AuditLog `ttl.cleaned`.
- Si un PDF se firma y reenvía exitosamente: status `sent`, mantenido hasta `ttl_at` igualmente (telemetría), pero ciphertext en R2 se borra inmediatamente.

## 4. Privacy & Threat Model

### 4.1 Invariantes de privacidad

| Invariante | Cómo se garantiza | Verificación |
|---|---|---|
| Backend nunca ve plaintext PDF | Evolution → backend recibe blob, lo cifra **antes** de tocar disco/DB con key derivada del OTP que el backend NO almacena (solo hash) | Test `webhook.test.ts` afirma que `r2.put` es llamado con buffer ≠ original; logs no contienen `%PDF-` |
| Backend no puede descifrar el blob de R2 sin OTP del user | OTP se hashea con Argon2id (no reversible); KDF(OTP, salt) = AES key; el OTP plaintext solo vive en Redis 10min como hash, jamás en DB | Test inyecta backend con DB+R2 dump y verifica que sin OTP, decrypt falla |
| Phone numbers están hasheados | `sender_phone_hash = HMAC-SHA256(e164, deploy_secret)`. Solo se almacena display masked al servir lista | Lint check: grep en migrations + serializers |
| Hard-delete real a 24h | Cron ttl-cleaner cada 5min + lifecycle R2 redundante a 25h | Test `ttl-cleaner.test.ts` con clock fake-timer |
| Audit log descifrable solo con clave de auditoría rotada | `AuditLog.payload_enc` = AES-GCM(JSON, deploy_audit_key); deploy_audit_key en SOPS, rotado mensual | Manual review trimestral |

### 4.2 Threats analizados

| Threat | Impacto | Mitigación |
|---|---|---|
| **T1**: Compromiso backend (RCE Fastify) | Atacante ve metadata + ciphertext + OTP hashes | Sin plaintext PDFs ni OTPs reversibles. Argon2id hace bruteforce de OTP costoso (~1s/intento × 10⁶ combinaciones). Rotación deploy_secret invalida todo el inventory hash a futuro. |
| **T2**: Compromiso R2 (credential leak) | Atacante baja ciphertexts | Sin OTP no descifra. Lifecycle 24h limita ventana. CF audit logs detectan pulls anómalos. |
| **T3**: Compromiso Evolution instance | Atacante ve PDFs en tránsito (antes de cifrado) | Aceptamos el riesgo: Evolution está en swarm interno, sin exposición pública directa, solo accesible desde el backend. Documentado para el user en `/como-funciona-wa`. |
| **T4**: Phone spoofing en Evolution | Atacante simula ser otro user | El sender phone se trata como público. El OTP es el único factor de auth. Adversario no obtiene PDFs ajenos solo spoofeando phone. |
| **T5**: Link OTP filtrado (forward accidental) | Quien tenga el link puede ver el PDF | El OTP es 6 dígitos = 10⁶ combinaciones; quien tiene el link tiene el OTP. Mitigación: TTL 24h + hard-delete tras firmar. Ampliable F3.6 con confirm vía SMS. |
| **T6**: Replay del webhook (Evolution comprometido) | Atacante inyecta PDFs falsos | HMAC validation + idempotency key (`message_id` único). |
| **T7**: DoS / spam | Saturar el bot | Rate limit 1 msg/30s/phone + 5 PDFs/día/phone (Redis token bucket). 429 con mensaje claro. |
| **T8**: Side-channel timing en OTP verify | Bruteforce online | Argon2id (intencionalmente lento) + Redis-backed exponential backoff (3-5-15-60-... segundos). Bloqueo phone tras 10 fallos en 1h. |
| **T9**: Shoulder-surfing en celular abierto | Tercero ve PDFs pendientes | Sesión JWT 15min + re-prompt OTP en cada `/inbox` cold-load. |

### 4.3 NO-mitigations (transparentes en `/como-funciona-wa`)

- **No defendemos contra Meta WhatsApp/Evolution viendo el PDF**: WA es E2E entre dispositivos, pero al usar un bot, Evolution descifra el mensaje en el servidor. El user lo acepta al usar el servicio.
- **No defendemos contra el dueño del celular del firmante**: si pierde el celular desbloqueado, lo demás pierde sentido.
- **No defendemos contra ataques quantum**: AES-256 sigue siendo cuántico-resistente para confidencialidad simétrica.

## 5. Quotas, rate limits y abuse

| Política | Valor | Implementación |
|---|---|---|
| Mensajes por phone | 1 / 30s | Redis token bucket key `rl:msg:<phone_hash>` |
| PDFs por día / phone | 5 | Redis counter key `rl:pdf:<phone_hash>:<YYYYMMDD>` reset 00:00 ECT |
| Tamaño PDF máximo | 20 MB | Validar en webhook antes de R2 PUT |
| OTP attempts | 10 / hora / phone | Redis key `rl:otp:<phone_hash>` |
| OTP TTL | 10 minutos (re-issue posible) | Redis SETEX 600 |
| JWT TTL | 15 minutos | jose lib exp claim |
| Inbox session re-prompt | cold-load (>10min idle) | client localStorage timestamp |

**429 response template**:
```json
{ "error": "rate_limited", "retry_after_s": 28, "user_message": "Espera 28 segundos antes de enviar otro PDF." }
```

Bot responde al user con el `user_message` en español.

## 6. Test strategy

### 6.1 Unit
- `inbox-crypto`: roundtrip + KAT (known-answer test) + tampering rejection (modificar 1 byte → tag mismatch).
- `otp.ts`: hash determinístico, salt único, Argon2id parámetros (m=64MiB, t=3, p=2).
- `phone-hash.ts`: mismo phone → mismo hash; phones distintos → hashes distintos; HMAC con secret rotado → hash distinto.
- `rate-limit.ts`: token bucket refill, edge case clock skew, atomic Lua script.

### 6.2 Integration (backend con docker-compose: postgres + redis + minio-as-r2 + mock evolution)
- `webhook.test.ts`: POST con HMAC válido → row creada + R2 object PUT + Evolution.send mock invocado.
- `webhook.test.ts`: HMAC inválido → 401, sin side effects.
- `webhook.test.ts`: replay con mismo `message_id` → 200 idempotente, sin duplicado.
- `outbox.test.ts`: JWT válido + signed PDF → Evolution.send mock recibido.
- `ttl-cleaner.test.ts`: insert row con `ttl_at = now()-1h` → cleaner borra row + R2 object.

### 6.3 E2E (Playwright)
- Spec `e2e/inbox-flow.spec.ts`:
  1. Mock webhook POST simulating Evolution sending a PDF.
  2. Extract OTP from mock Evolution.send call.
  3. Navigate `app.firmar.ec/inbox?t=<OTP>` (staging).
  4. Verify list shows 1 PDF.
  5. Click "Firmar" → flow F3 with `.p12` test fixture.
  6. Click "Reenviar al original" → assert mock Evolution.send called with signed PDF.
  7. Verify cleanup: after 24h fake-timer, list shows 0 PDFs.

### 6.4 Privacy invariants
- `privacy.test.ts`: full happy path → query DB raw + R2 raw → grep `%PDF-`, grep plaintext-OTP, grep e164 phone → must return 0 hits.
- `privacy.test.ts`: backend logs en stdout/stderr filtrados → mismo grep, 0 hits.

### 6.5 Performance / load
- k6 script: 100 webhook RPS por 1min — p95 latency <500ms, error rate <0.1%.
- TTL cleaner: 10k rows expiradas → batch DELETE en <30s.

### 6.6 Security
- ZAP scan del webhook + outbox endpoints.
- Trivy/Grype scan del Dockerfile.
- Mozilla Observatory en `inbox.firmar.ec` ≥ A.
